# Отчёт о тестировании — PRIDE ONE Booking Bot 2.0.2

Дата прогона: 10 ноября 2026. Окружение: Node.js 22.23.4, встроенный SQLite 3.53 (`node:sqlite`).

## Что нового в 2.0.2

После успешной отмены записи бот публикует в группе новое сообщение внизу чата:

```
Запись отменена
Ребёнок: <имя>
Дата: <дата>
Время: <время>
```

- Всплывающее подтверждение родителю (`answerCallbackQuery`) работает как раньше и не зависит от
  доставки уведомления. Прокрутить чат родителя Bot API не умеет, на это расчёта нет.
- Защита от дублей: задача outbox с ключом `cancel_notice:<id брони>` ставится **только** при переходе
  брони из `active` в `cancelled`, в той же транзакции. Повтор webhook (`update_id`), повторное нажатие
  на отменённую запись и повторная обработка outbox второго уведомления не создают.
- После отправки сохраняется отметка в таблице `meta`: если завершить задачу не удалось, повтор
  не отправляет второе сообщение. Отметки удаляются через 7 дней.
- Проверка владельца записи, обновление исходного сообщения, общего списка дня и панели не менялись.

**Изменён один файл кода: `src/branch-do.js`.** `src/index.js` и `wrangler.jsonc` побайтно совпадают
с 2.0.1 (проверено `cmp`). Схема SQLite, расписание, правила записи и миграция не менялись.

## Где выполнялись тесты

Как и раньше, **локально в эмуляторе** (`test/emulator.mjs`): настоящий SQLite в файле, транзакции
BEGIN/COMMIT/ROLLBACK, перезапуск объекта с потерей памяти, будильник, параллельные RPC-вызовы
(`Promise.all`), мок Telegram Bot API с внедрением сбоев (сеть, 5xx, 429, 400/403, «зависание»,
«потерянный ответ после доставки»). **Не в Cloudflare и не в `workerd`.** В окружении нет доступа к
npm-реестру, поэтому `wrangler` не устанавливался: `npm run build:dry` здесь **не запускался**.

Чего эмулятор не проверяет: поведение реального `workerd` (входные ворота, лимиты CPU), реальный
Telegram (упоминания, права на удаление сообщений, лимиты на группу), реальный KV, точный вывод
`wrangler deploy` при уже применённой миграции.

### Что доказывают новые тесты U (уведомление об отмене)

- **U1 — кнопка в подтверждении.** Ровно одно уведомление; точный текст; без кнопок; не ответ на
  чьё-то сообщение; отправлено в группу филиала; это самое нижнее сообщение чата. Всплывающее
  «Запись отменена», правка подтверждения, общий список дня и счётчик панели — как раньше.
- **U2 — кнопка в «Мои записи».** То же, плюс обновлён сам список «Мои записи».
- **U3 — старый формат кнопки** `cancel|дата|id` (записи, оформленные раньше).
- **U4 — повторные webhook.** Тот же `update_id` приходит параллельно и позже, для обоих сценариев
  отмены: одно уведомление на каждую отмену.
- **U5 — повторное нажатие на уже отменённую запись** (новые `update_id`, устаревшие кнопки в обоих
  сообщениях): «Эта запись уже отменена.», нового уведомления нет, в outbox нет новых задач,
  Telegram не просили отправлять сообщение.
- **U6 — одновременные нажатия** из подтверждения и из «Мои записи»: одно уведомление, одно
  «Запись отменена» и два «уже отменена».
- **U7 — ключ привязан к броне.** Два ребёнка — два уведомления; повторная запись того же ребёнка и
  новая отмена — ещё одно (три разных ключа).
- **U8 — дедупликация в самой базе.** Второй ожидающий `cancel_notice` с тем же ключом не
  вставляется; после перезапуска объекта пять одновременных запусков outbox дают одно сообщение.
- **U9, U10 — запреты.** Чужая запись (все три вида кнопок), неизвестная бронь, кнопка из другого
  чата, занятие уже началось: отмены нет, уведомления нет.
- **U11 — всплывающее подтверждение не зависит от уведомления:** отправка уведомления «зависла», а
  подтверждение родителю уже показано и отмена сохранена.
- **U12, U13 — сетевая ошибка до доставки, 502, 429 (`retry_after`).** Повторы с задержкой и паузой,
  итог — одно уведомление.
- **U14 — потерянный ответ Telegram после доставки.** **Известное ограничение API, зафиксированное
  тестом:** возможна ровно одна лишняя копия (итого 2), дальше новых копий нет — ни от будильников,
  ни от повторного нажатия. На бронь и списки это не влияет.
- **U15 — уведомление отправлено, но завершить задачу не удалось (ошибка SQL).** Повтор видит
  отметку и второе сообщение не отправляет.
- **U16, U17 — перезапуск объекта** во время отправки и между сохранением отмены и отправкой:
  уведомление уходит один раз, повторный webhook его не дублирует.
- **U18 — постоянная ошибка (403).** Задача `failed` видна в `/admin/status`, отмена цела, повторов нет.
- **U19 — ошибка SQL при самой отмене.** Откат целиком: нет отмены, нет уведомления, `update_id` не
  отмечен; повтор update проходит.
- **U20 — очистка отметок через 7 дней** (через сутки они ещё на месте).

### Что доказывают тесты V (обновление и откат)

Код 2.0.1 — замороженная копия в `test/fixtures/`. Новая версия «разворачивается» над теми же
файлом SQLite и будильником, память экземпляров теряется (как при обновлении кода в Cloudflare).

- **V1.** Данные, созданные 2.0.1 (брони, отмена, история, формы, сообщения бота), после обновления
  **побайтно те же** (сравнение всех таблиц и всех определений таблиц и индексов). Обновление ничего
  не публикует в группе. Новая отмена даёт уведомление, прежняя отмена задним числом — нет.
- **V2.** Обновление после миграции KV: повторная миграция возвращает `alreadyDone`, данные и KV не
  меняются; бронь, перенесённая из KV, отменяется кнопкой старого формата с уведомлением.
- **V3.** Задачи outbox, не завершённые до обновления, выполняет новая версия.
- **V4.** Откат на 2.0.1: брони целы, ожидающее `cancel_notice` старая версия помечает выполненным без
  отправки (уведомления в 2.0.1 не публикуются), очередь не ломается, запись продолжает работать.

## Что требует проверки на вашей стороне

1. `npm ci`, `npm test`, `npm run check`, `npm run build:dry` (шаг 3 в `UPDATE_2.0.2.md`).
2. Вывод `wrangler deploy` при обновлении: там не должно быть создания, переименования или удаления
   класса Durable Object. Точный текст вывода в этом случае я проверить не мог.
3. Работа в реальном Telegram: что уведомление действительно оказывается внизу чата, права бота.
4. Лимит Telegram (около 20 сообщений в минуту на группу): каждая отмена добавляет одно сообщение,
   при массовых отменах сообщения придут с задержкой — данные не пострадают.
