# Обновление PRIDE ONE Booking Bot: 2.0.1 → 2.0.2

Для Worker, который уже развёрнут по `FIRST_RUN.md` и работает. Первый запуск с нуля — в `FIRST_RUN.md`.

## Что меняется

**Новое:** после успешной отмены бот публикует в группе новое сообщение внизу чата:
```
Запись отменена
Ребёнок: <имя>
Дата: <дата>
Время: <время>
```
Остальное — как в 2.0.1: всплывающее подтверждение родителю, правка исходного сообщения, обновление
общего списка дня и панели, проверка владельца записи.

**Что НЕ меняется** (проверено сравнением файлов с 2.0.1):
- `src/index.js` — идентичен;
- `wrangler.jsonc` — идентичен: миграция `v1`, привязки, переменные, cron не тронуты;
- схема SQLite (таблицы, индексы) — без изменений;
- `migrations` — новых записей нет, поэтому **новая миграция Durable Object не создаётся**;
- данные записей, формы, история, outbox — не затрагиваются.

Изменён один файл кода — `src/branch-do.js`. Для хранения отметок об отправленных уведомлениях
используется уже существующая таблица `meta` (ключи `cancel_notice:<id брони>`, удаляются через 7 дней).

## Чего НЕ делать

- **Не разворачивать `wrangler.jsonc` из архива, если в нём заглушки.** В свежей распаковке архива
  `ВСТАВЬТЕ_ID_…` вместо ваших значений: `wrangler deploy` заменил бы `BRANCH_CHATS` и ID KV
  заглушками, и бот перестал бы отвечать в группе. Поэтому ниже файлы копируются **в вашу рабочую папку**
  с настоящими значениями, а `npm run check` (строгий) заглушки не пропускает.
- Не менять и не удалять запись `{"tag": "v1", …}` в `migrations`; не добавлять новых тегов.
- Не запускать `/admin/migrate` (с `dry_run=0` — вернёт `alreadyDone`; параметр `force=1` не использовать).
- Не удалять Worker, Durable Object и KV (`wrangler delete`, удаление namespace).
- Не передавать `--secrets-file`: секреты (`BOT_TOKEN`, `WEBHOOK_SECRET`, `ADMIN_SECRET`) уже в Cloudflare
  и сохраняются при развёртывании.

Во всех командах `<URL>` = `https://pride-one-bot.rustik-yuldashev.workers.dev`, `<ADMIN_SECRET>` — ваш
секрет. В Windows PowerShell пишите `curl.exe` вместо `curl`.

## Шаг 1. Снимок состояния ДО обновления — только чтение

```
curl -H "Authorization: Bearer <ADMIN_SECRET>" "<URL>/admin/status?branch=P03" > status-before.json
npx wrangler deployments list --name pride-one-bot
```
Сохраните `status-before.json` и запишите ID текущей версии. В `status-before.json` важны:
`schema_version` ("1"), `bookings` (число активных и отменённых броней), блок `migration`
(`verified: true`, `migrated_at`), `outbox.failed` (должно быть 0).

Встроенной команды выгрузки SQLite у бота нет, а само обновление данных не касается. Если нужна
страховка, зафиксируйте число броней в этом файле и сверьте его после обновления.

## Шаг 2. Обновить файлы в рабочей папке проекта

Распакуйте `pride-one-bot-v2.0.2.zip` в **отдельную** папку и скопируйте оттуда в вашу рабочую папку
(та, из которой вы делали первый `wrangler deploy`, с настоящим `wrangler.jsonc`):

| Файл из архива | Обязательно? |
|---|---|
| `src/branch-do.js` | **да** — единственное изменение кода |
| `test/cancel-notice.test.mjs`, `test/upgrade.test.mjs`, `test/fixtures/branch-do-2.0.1.js`, `test/harness.mjs`, `test/emulator.mjs`, `test/mutation-check.sh` | для запуска 64 тестов (рекомендуется; папку `test/fixtures` создайте, если её нет) |
| `UPDATE_2.0.2.md`, `README.md`, `TEST_REPORT.md` | документация |

Не копируйте `wrangler.jsonc`, `package.json` и `package-lock.json` — в них ваши рабочие значения и
закреплённая версия wrangler. Чтобы `npm test` запускал новые тесты, в вашем `package.json` в строке
`"test"` добавьте в конец `test/cancel-notice.test.mjs test/upgrade.test.mjs` (и по желанию поменяйте `"version"` на `2.0.2`):

```
"test": "node --no-warnings --import ./test/register.mjs --test --test-concurrency=1 test/bot.test.mjs test/messages.test.mjs test/cancel-notice.test.mjs test/upgrade.test.mjs",
```

## Шаг 3. Проверки перед развёртыванием — в Cloudflare ничего не меняется

```
npm ci
npm test
npm run check
npm run build:dry
```
- `npm test` → `pass 64`, `fail 0` (в том числе 4 теста обновления и отката на одних данных SQLite);
- `npm run check` — строгий режим на вашем настоящем `wrangler.jsonc`: должно быть «ошибок 0» (он же
  проверяет, что нет заглушек, что миграции — только `new_sqlite_classes`, что секретов нет в `vars`);
- `npm run build:dry` — сборка без публикации. Это единственная команда из списка, которую я не мог
  запустить в своём окружении (нет доступа к npm).

Если что-то из этого не прошло — не разворачивайте и пришлите вывод.

## Шаг 4. Развёртывание — единственный шаг, меняющий код в Cloudflare

Лучше в спокойное время (когда в группе не записываются).
```
npx wrangler deploy
```
Что произойдёт и что проверить:
- Код Worker и Durable Object заменяется. **SQLite-данные сохраняются:** по документации Cloudflare при
  обновлении кода объект перезапускается, теряется только память экземпляра, а данные `storage` остаются.
- Миграция `v1` уже применена и не менялась, поэтому в выводе не должно быть создания нового класса.
  Точный вывод Wrangler для этого случая я проверить не мог. Если он сообщит о создании, переименовании
  или удалении класса Durable Object — не продолжайте и пришлите вывод.
- Если Wrangler покажет различия между конфигурацией в Dashboard и локальным файлом, внимательно прочитайте
  список. Файл — ваш рабочий `wrangler.jsonc`, ему и следует Cloudflare.
- Запрос, который обрабатывался в момент перезапуска объекта, может завершиться ошибкой
  `Durable Object reset because its code was updated`. Worker ответит Telegram 500, Telegram повторит
  update, а повторная доставка безопасна (защита по `update_id`). Задачи outbox, не успевшие
  отправиться, подхватит будильник объекта.

## Шаг 6. Проверка в Pride Test

1. Родитель записывает ребёнка → приходит подтверждение. Нажимает «Отменить эту запись»:
   - сразу появляется всплывающее «Запись отменена»;
   - внизу чата появляется **новое** сообщение «Запись отменена / Ребёнок / Дата / Время»;
   - исходное подтверждение стало «Запись отменена.», ребёнок исчез из общего списка дня, счётчик в панели уменьшился.
2. Другой ребёнок: отмена через «Мои записи» → то же самое, плюс обновился сам список «Мои записи».
3. Нажать ту же кнопку отмены ещё раз → «Эта запись уже отменена.», **нового сообщения нет**.
4. Другой родитель пытается отменить чужую запись → отказ, сообщения нет.
5. После проверок снова `/admin/status`: `outbox.failed` = 0.

Записи, отменённые до обновления, уведомлений задним числом не получают.

## Откат

Данные и схема не менялись, поэтому откат безопасен:
```
npx wrangler rollback
```
(выберите версию 2.0.1 из `deployments list`). Откат между версиями 2.x допустим: границу миграции `v1`
он не пересекает. В 2.0.1 отметки `cancel_notice:*` в `meta` игнорируются, а ожидающие задачи
`cancel_notice` старый код помечает выполненными без отправки. Ничего не ломается, но уведомления
перестанут публиковаться.

## Известное ограничение

Если Telegram доставил уведомление, но ответ потерялся, бот отправит его повторно: в группе окажется
**одна** лишняя копия. У `sendMessage` нет ключа идемпотентности, этого не обойти. Все остальные сбои
(сеть, 5xx, 429, перезапуск, повтор webhook, ошибка SQL) дубля не создают. Лишнюю копию можно удалить
вручную.
